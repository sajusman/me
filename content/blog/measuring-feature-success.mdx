The most expensive mistake in consumer engineering isn't a bug. It's shipping a
feature nobody can tell whether it worked. You spend three weeks building, it goes
live, and then… vibes. Someone says it "feels" better. Someone else isn't sure.

The fix is to make a feature _evaluable_ before you write it.

## Write the hypothesis, not the ticket

Before building Faircado's visual search, the question wasn't "build image
search". It was:

> If users can search by pointing at an object, image-search users will come back
> more often than users who only use text search.

That single sentence gives you everything:

- **Who**: image-search users
- **What changes**: retention
- **The comparison**: vs text-only users

If you can't write that sentence, you don't understand the feature well enough to
build it yet.

## Pick one primary metric — and guardrails

Every feature gets exactly one number it's trying to move, plus a couple of
guardrails it must not break.

```ts
type FeatureBet = {
  primary: string;        // the one metric this feature moves
  guardrails: string[];   // metrics that must NOT regress
  target: number;         // what "worked" looks like
  window: string;         // how long we measure before deciding
};

const visualSearch: FeatureBet = {
  primary: "d7 retention (image-search cohort)",
  guardrails: ["checkout conversion", "search latency p95", "crash-free rate"],
  target: 0.25, // +25% retention
  window: "4 weeks",
};
```

The guardrails are the part people skip. A feature that lifts retention 25% but
tanks checkout conversion is not a win — it's a trade you have to make on purpose,
not by accident.

## Instrument for the cohort, not the average

Averages hide everything. The users who touch a feature are almost never a random
sample. When I wired Mixpanel events for visual search, I tracked the _image-search
cohort_ specifically, because folding them into the global retention number would
have washed out the entire signal.

## Decide the decision in advance

Write down what you'll do at each outcome _before_ you look at the data:

- **Hits target** → invest more, expand surface area.
- **Moves but under target** → keep, but stop investing.
- **Flat or negative** → roll back, write down why, move on.

Pre-committing to the decision is what stops "well, it's kind of working" from
keeping dead features alive forever.

## The uncomfortable truth

Most features don't move the number. That's fine — that's what shipping small and
measuring honestly buys you: the ability to kill the misses fast and pour into the
hits. A feature written to be evaluated is a feature you can be wrong about
cheaply.
